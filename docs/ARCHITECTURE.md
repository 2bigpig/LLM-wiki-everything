# 首版实现架构

当前从空仓库建立应用 → 首版目标是保存、读取、分析、关联、Wiki 维护及事后纠正形成完整流程。

## 组件职责

采用模块化单体，共享 Python 业务代码，以不同进程承担 API、队列与推理职责。

运行方式：FastAPI 和 Worker 在 Windows 本地 Python 虚拟环境运行，前端在本地 Vite 运行。Docker 只运行 PostgreSQL + pgvector、GPU OCR、GPU ASR 和 CPU BGE-M3，不构建业务后端镜像。

宿主机默认通过 5432/8101/8102/8103 回环端口访问数据库与模型；端口和运行调优参数统一在根目录 config.yaml 管理，.env 只保存数据库密码、模型密钥与访问口令。统一配置模块负责校验、地址派生和容器环境注入，Vite 只读取公共服务参数，业务代码通过 settings.xxx 引用。详见 [配置说明](CONFIGURATION.md)。OCR/ASR 只读挂载宿主机 paths.data_dir，双方使用相同相对 storage_key，避免 Windows/Linux 绝对路径差异。BGE-M3 只接收文本并返回向量，缓存继续使用 llm-wiki_embeddings 卷。

- API：输入校验、读取结果、编辑、恢复与提交持久化待办。
- Procrastinate：持久化排队、按执行 ID 加锁、处理进程心跳及停滞任务重新调度。
- LangGraph：以每次分析执行 ID 为 thread_id，保存阶段检查点并恢复未完成节点。
- 业务服务：原件版本、引用校验、关系反馈、Wiki 乐观并发和版本快照。
- 推理服务：独立依赖镜像，持有全局 GPU 锁并运行一次性模型子进程。
- 向量服务：独立 CPU 镜像，串行小批量编码；后端校验模型名、向量数量、1024 维和有限数值后才写入数据库。
- PostgreSQL：业务数据、向量、检查点与队列。文件系统只保存附件、衍生文件和模型缓存。

## 数据与一致性

原始记录的每次修改增加版本。读取片段的身份由记录、来源版本、附件或原文位置及顺序确定；旧片段不因新版本被删除。

处理执行记录与内容保存同事务提交，执行记录兼作持久化待办。独立派发器反复提交队列，队列锁限制重复排队和并行执行；恢复后的各业务阶段仍自行检查已有结果。

模型成功输出按执行与请求指纹复用。模型调用前在数据库中保守预留 Token，未知响应不当作零费用。所有引用必须落在当前任务提供的来源集合内；关联的两侧引文必须能在原始片段中核对。

Wiki 自动正文与个人笔记分开。自动更新使用生成时的页版本提交；版本不匹配则停止更新并保留既有数据。每次人工修改、AI 更新与恢复都建立新快照。

个人库的自动 Wiki 维护使用全局会话锁串行执行，避免短时间多条资料更新同一页时重复生成。人工编辑仍通过版本检查保护。记录锁采用 NO KEY UPDATE，允许其他任务核对关系外键；关系使用数据库 upsert 合并并发发现，保留人工反馈。

检查点与业务事务分别提交，因此检查点本身不承担业务去重。成功分析每个执行唯一，Wiki 同一执行对同一页面只提交一次。

## 读取与检索

按输入组合读取正文、字幕、文件、OCR 与 ASR。长内容分组分析，再综合各组结果；中间模型结果可以复用。实际覆盖范围随记录展示，部分读取不会显示成完整读取。

中文关键词由 jieba 切分，PostgreSQL 全文索引召回；可选 BGE-M3 稠密向量召回，使用 RRF 合并结果。搜索过滤过期来源版本及归档记录，旧引用仍可单独访问。

## 首版约束

- 本地 API/Worker 分别写入滚动日志；request_id 关联 HTTP 与模型调用，run_id 关联后台阶段，日志不记录用户正文和模型密钥。

- 单卡重任务串行，默认 CPU 生成嵌入。
- 普通任务通过进度轮询展示，后续可根据真实需求增加流式输出。
- 个人规模下部分 Wiki 目录操作扫描页标题，达到规模瓶颈后再增加主题召回索引。
- 自托管仅默认开放回环端口，模型密钥保存在服务端。新增远程部署或多人使用需单独设计账号和权限。
- 真实质量评估独立于代码测试；离线测试替身只验证流程、引用与失败语义。
